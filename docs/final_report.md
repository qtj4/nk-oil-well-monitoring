# Анализ режимов работы нефтяных скважин

Итоговый проект по Programming for Data Analysis and Database. Applied Artificial Intelligence, магистратура.

Аннотация. Разработана локальная система анализа исторических датчиков десяти скважин месторождения NK. Приложение связывает подготовку данных, SQLite, визуальный анализ и обнаружение кандидатов на смену режима. Полный набор содержит 258 387 наблюдений параметров за январь-сентябрь 2026 года. Сохранено официальное хронологическое разбиение, выполнены восемь аналитических SQL-запросов, сопоставлены отсутствие изменений, rolling shift и CUSUM. Проверенные метки неисправностей отсутствуют; результаты характеризуют статистические события, а не точность диагностики отказов.

Исследовательские вопросы: как различаются доступные датчики фонтанных и насосных скважин; какие изменения сопровождаются признаками качества данных; как обеспечить воспроизводимый анализ на обычном CPU-ноутбуке; как сохранить решение аналитика и связать его с исходными наблюдениями.

Наблюдаемое изменение режима определяется как устойчивое изменение распределения сигнала. Одиночный выброс и смена масштаба измерения могут создавать похожие признаки. Проект не устанавливает физическую причину и не управляет оборудованием.

Основание отчета: фактически исполненный run 20261112T171150743233Z_full. Точная конфигурация, версии и хеши сохранены в run_manifest.json. Числа ниже вычислены по его таблицам.

Авторы и распределение вклада: сведения не предоставлены. Перед сдачей вписать реальные имена и подтвержденный вклад; вымышленные участники не указаны.

## 1. Источник, структура и воспроизводимость

Источник: Arailym Tleubayeva, NK Oil Well Sensor Monitoring v2, Hugging Face. Поставщик данных: Galaz and Company LLP. Apache-2.0; сохраняются дополнительные условия владения и конфиденциальности исходных данных. Карточка и API-метаданные сохранены локально. Исходный год назначен авторами по последовательности файлов и требует сверки с SCADA. Часовой пояс не документирован; временные метки оставлены без timezone.

| Показатель | Измеренное значение |
| --- | --- |
| Период | 2026-01-01 00:00:00 / 2026-09-30 23:00:00 |
| Строки train / test | 206,706 / 51,681 |
| Скважины / пары скважина-параметр | 10 / 43 |
| Формат | Один параметр одной скважины за час |
| Исходные CSV / long Parquet | 19,845,754 / 2,180,136 байт |
| Оптимизированный Pandas long | 9.800 MB |

Фонтанные скважины: NK-75, NK-76, NK-83; доступны давления в atm. Семь насосных скважин имеют SPM (strokes/min), заполнение насоса (%), нагрузки на штангу (kg), площадь динамограммы (unitless). У NK-76 отсутствует casing_pressure. Сравнивать средние разных параметров как одну физическую величину нельзя.

Столбцы: well_id, well_type, timestamp, parameter, value, unit, n_obs, flag. Ключ: well_id + parameter + timestamp. Дубликаты отклоняются, а не усредняются молча. Месячная выборка сохраняет первые десять дней каждого месяца: 85 423 реальные строки, все скважины. Она включает окно 8 мая и июнь; ее искусственно исключенные даты не являются сбоями источника.

Источник меньше рекомендованных 500 000 строк или 200 MB. Данные не размножались. Для формального соответствия этому пункту требуется разрешение преподавателя либо дополнительный легитимный источник.

Проверено 258,387 строк: дубликатов ключа 0; NULL sensor values 0. При этом найдено 21,014 отсутствующих часовых слотов внутри наблюдаемых границ каждой пары скважина-параметр. Это сумма отсутствий параметров, не число общих часов простоя и не число NULL. Частоты source flags приведены ниже.

Площадь динамограммы исключена из основного сравнения методов; отдельно сохранены чувствительность к ее включению и к сохранению flagged-записей.

## 3. Архитектура и база данных

Python 3.12: chunked CSV -> валидация -> long/wide Parquet -> нормализованная SQLite -> EDA и CPU-методы -> Streamlit/Plotly. Подготовка выполняется CLI. Приложение читает готовые артефакты, кеширует их по fingerprint и не обучает методы при фильтрации. Отдельный JavaScript frontend, микросервисы и GPU не требуются.

Основные сущности: wells(well_id PK, well_type); parameters(parameter PK, unit); observations(well_id FK, parameter FK, timestamp, value, n_obs, split). Составной PK наблюдения предотвращает инфляцию строк. flag_types и observation_flags нормализуют составные флаги, а исходная строка flag сохраняется для аудита. Индекс timestamp ускоряет диапазоны. ER-схема Mermaid: docs/database_design.md.

| SQL-файл | Назначение и конструкция |
| --- | --- |
| 01_coverage | JOIN wells/parameters, полнота по паре |
| 02_monthly | GROUP BY скважина, параметр, месяц |
| 03_flagged_groups | GROUP BY / HAVING flagged > 0 |
| 04_gaps | CTE и LAG по скважине + параметру |
| 05_causal_rolling | AVG по 24 предшествующим записям |
| 06_flags | Частоты исходных флагов |
| 07_type_summary | JOIN и группировка по типу / параметру |
| 08_latest | CTE + ROW_NUMBER, последнее наблюдение |

Все восемь запросов реально исполнены в SQLite и возвращены в Pandas. LAG измеряет интервалы между существующими timestamp, а не NULL значений. Окно 24 ROWS означает 24 записи, не гарантированно 24 часа.

Решения аналитика хранятся отдельно: analysis_runs, events, event_runs, alert_reviews в data/reviews.sqlite. Идентификатор события зависит от данных, конфигурации, метода и временного бина. Повторная индексация не стирает заметки. Статусы проверяются, SQL параметризован, HTML заметок экранируется.

## 4. Подготовка и протокол методов

CSV читается блоками по 25 000 строк; категориальные идентификаторы снижают память без изменения float64 значений. Временная точность сохраняется. Long->wide pivot включает скважину в индекс; 258,387 непропущенных значений сверены точно, получено 63,470 строк скважина-час. Ничего не смешивается между скважинами.

Официальная граница: train до 2026-08-08 22:00 включительно, test с 23:00. Нет shuffle. Для методов используются дневные медианы с минимум 12 unflagged записями. Бин 8 августа исключен, поскольку пересекает границу. Дневной timestamp обозначает начало бина; медиана и событие доступны только после завершения дня.

| Метод | Определение и фиксированные настройки |
| --- | --- |
| No change | Пустое множество кандидатов; контроль отсутствия детекции |
| Rolling shift | |x_t - mean(x_(t-3:t-1))| / s_train > 3 |
| CUSUM | Две суммы отклонений от train median; drift=0.5, h=5 |
| Общее | Train MAD*1.4826, fallback std/floor; cooldown 7 дней |

Нормализатор fit только на train; в test параметры заморожены. Rolling-история использует только предшествующие дни и сбрасывается через разрыв. Для CUSUM также сбрасывается накопленное состояние. Маркер внутри train ретроспективен, поскольку использует обучающий период целиком. Это отдельно обозначено, и train-события не используются как оценка хронологической точности.

Метки истинных смен режима/отказов не обнаружены. Precision, recall и F1 не вычисляются. MAE не относится к этой задаче без численной прогнозной цели. Сравнение показывает число кандидатов, частоту, чувствительность к порогу и измеренные ресурсы на одинаковом наборе единиц.

Дополнительная аналитика характеризует события по окнам +/-7 дней: медиана, вариативность, сдвиг уровня, плотность flags, отсутствия/NULL и расстояние до следующего кандидата. Следующее окно используется только для ретроспективного объяснения, не подается детектору и не становится меткой неисправности.

## 5. Сопоставление методов

Общая тестовая область: 1 747 допустимых скважина-параметр-дней. Конфигурации заморожены до тестового запуска. Результаты ниже относятся к кандидатам по выбранным датчикам и фильтрам, а не к количеству реальных аварий или физических режимов.

| Метод | Train | Test | На 100 test дней | Секунды |
| --- | --- | --- | --- | --- |
| no_change | 0 | 0 | 0.00 | 0.0004 |
| rolling_shift | 129 | 29 | 1.66 | 0.1604 |
| cusum | 384 | 139 | 7.96 | 0.1118 |

Figure: deliverables/figures/methods.pdf; source results/20261112T171150743233Z_full/.

| Чувствительность порога | 80% | 100% | 120% |
| --- | --- | --- | --- |
| no_change | 0 | 0 | 0 |
| rolling_shift | 39 | 29 | 21 |
| cusum | 148 | 139 | 125 |

CUSUM создает больше кандидатов, в том числе повторные уведомления при длительном отклонении от train reference после cooldown. Это не доказывает превосходство чувствительности или качества. No-change закономерно дает ноль. По этим диагностическим числам нельзя ранжировать точность без независимой экспертной разметки. Изменение порогов служит проверкой чувствительности; порог не выбирался по test-результатам.

## 6. EDA и интерпретация масштаба

Figure: deliverables/figures/area.pdf; source results/20261112T171150743233Z_full/.

Соотношения медиан апреля и мая составляют примерно 9.95-20.37 в семи насосных скважинах. Окна карточки источника и ее приблизительные примеры отличаются от этих точных месячных окон. Наблюдаемая синхронность поддерживает гипотезу смены масштаба/калибровки, но не устанавливает причину. Автоматическая коррекция коэффициентом не применяется.

EDA сохранена как descriptive_statistics.csv, daily_patterns.csv и пять HTML-графиков: временной ряд с предшествующим средним, распределение по скважинам и типам, профиль часа суток, корреляции одной скважины, матрица source flags. Средние профилей объединяют наблюдения с неодинаковым покрытием; счетчики count позволяют увидеть эту неоднородность.

Корреляции считаются только по совпавшим timestamp одной скважины при минимум 24 парах. Матрица количества пар сохранена отдельно. Корреляция не доказывает причинность, а масштабирование площади и сезонная/операционная структура могут влиять на результат. У типов скважин разные наборы датчиков: сравнивать можно покрытие и структуру доступных наблюдений; давления и SPM нельзя ставить на одну физическую шкалу.

Заявленные в карточке многодневные провалы и общие отключения исследуются экспортом LAG. Для sample-режима разрывы отбора отмечены отдельно и не интерпретируются как реальный простой.

Короткие пики могут быть пропущены. Базовая память Python/библиотек включена. CSV ingest содержит валидацию; Parquet reread ее не повторяет. CPU Windows-ноутбук, Python 3.12, около 6.29 GB установленной RAM. GPU не использовался. Рабочие версии зависимостей закреплены requirements.txt. Повторный полный запуск дал те же объемы и количество кандидатов; run_manifest сохраняет конфигурации, source/data hashes и версии.

21 тест проходит, включая реальный UI review->save->reload->report, все SQL, pivot, разделение скважин, ошибочные даты, неизвестные flags, защиту от future/test leakage, официальные file hashes, временные разрывы, пустые состояния и автономную загрузку sample. Синтетические fixtures используются только в тестах; аналитические результаты взяты из источника.

Запуск: python -m nk_oil.cli prepare --mode sample; python -m nk_oil.cli enhance --mode sample; python -m streamlit run app.py. Полный режим: fetch, затем prepare/enhance --mode full. На Windows следует использовать .venv/Scripts/python.exe. Полные команды и типовые ошибки: README.md.

## 8. Выводы, ограничения и источники

Получен воспроизводимый аналитический инструмент: исходные значения проверены, SQL и Parquet согласованы, известные изменения исследованы на полном наборе, кандидаты связаны с сохраненными решениями аналитика. Без GPU приложение работает на ограниченном ноутбуке и демонстрируется автономно.

Главные ограничения: отсутствуют подтвержденные отказы, журнал обслуживания и дебит; возможен сдвиг калибровки; год и timezone не подтверждены оператором; датасет меньше рекомендации курса; агрегация по дням теряет внутрисуточные изменения. Окна описания событий ретроспективны. Аналитические уведомления и статус confirmed не являются ground truth и не должны управлять оборудованием.

Следующая исследовательская работа: независимая экспертная разметка, проверка временной привязки в SCADA, отделение смены масштаба от технологического процесса и согласование достаточности размера с преподавателем. Финальная оценка выставляется преподавателем; эвристический аудит проекта не является оценкой курса.
